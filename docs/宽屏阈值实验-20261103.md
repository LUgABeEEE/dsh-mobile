# 宽屏阈值实验：按「短边」判定，避免横屏手机被当成平板

实验分支 `exp/wide-by-shorter-side`（从 `upstream/main` = 0.8.1 / `42cabbd` 切出），只推 fork `LUgABeEEE/dsh-mobile`，未建 PR、未改 upstream。

这是一份实验记录，不是发布文档；因此没有 `.en.md` 对照，也没有写进 `docs/README.md` 的专题索引与 `CHANGELOG.md`（0.8.1 已发布，本次不是 release 内容）。

## 结论

| 视口 | 改前 | 改后 | 依据 |
| --- | --- | --- | --- |
| 932×430（横屏手机） | 宽布局：侧栏常驻 340/56px、无返回栏 | 抽屉布局：侧栏浮层、面板返回栏回归 | 【实测】Chromium 见下方几何表 |
| 909×1314（竖屏平板） | 宽布局 | 宽布局（不变） | 【实测】 |
| 1363×860（横屏平板） | 宽布局 | 宽布局（不变） | 【实测】 |
| 390×844 / 900×599 / 900×600 | 窄 / 宽 / 宽 | 窄 / 窄 / 宽 | 【实测】边界精确 |

判定条件：`宽度 ≥ 900 且 min(宽, 高) ≥ 600`。宽度已 ≥900 时短边就是高度，所以等价于 CSS 的 `(min-width:900px) and (min-height:600px)`——**媒体查询与 JS 判定用同一组常量生成**，不是两份手写的数字。

## 改动点

### 1. 判定与查询常量 · `src/mobile-layout.ts:89-131`

- 新增 `WIDE_LAYOUT_MIN_SHORTER_SIDE_PX = 600`（`:97`）。
- 新增 `WIDE_LAYOUT_QUERY`（`:104`）= `(min-width:900px) and (min-height:600px)`，CSS 与 `matchMedia` 共用。
- 新增 `NARROW_LAYOUT_QUERY`（`:106`）= `(max-width:899px),(max-height:599px)`，宽判定的补集。
- 新增 `FOLDED_RAIL_OFFSET_QUERY`（`:113`）= 原 `(min-width:721px) and (max-width:899px)` 加上 `(min-width:721px) and (max-height:599px)`。
- `isWideViewportLayout(viewportWidth, viewportHeight)`（`:128`）：`width >= 900 && Math.min(width, height) >= 600`。
- `resolveMobileRightbarLayout` 增加 `viewportHeight` 形参（`:140-152`），内部复用一次 `wide` 判定，不再三处重复调用。

### 2. CSS 两处 `@media(min-width:900px)` 同步

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| `:561`（`@layer dsh-mobile-layout` 内的网格所有权） | `@media(min-width:900px)` | `@media${WIDE_LAYOUT_QUERY}` |
| `:632`（宽布局块：drawer 静态列、main 第 2 列） | `@media(min-width:900px)` | `@media${WIDE_LAYOUT_QUERY}` |

`MOBILE_LAYOUT_STYLES` 是模板字符串，常量在模块加载时插值，构建产物里就是字面量 `@media(min-width:900px) and (min-height:600px){`。

### 3. 两处必须一起动的窄带规则

- `:591` `.dshm-details` 全宽规则：`@media(max-width:899px)` → `@media${NARROW_LAYOUT_QUERY}`。不跟着改，横屏手机进抽屉布局后右面板仍是 94vw 浮层、48px 触控目标也不生效。
- `:585` 折叠图标轨 56px 偏移：原规则只覆盖 721-899px。横屏手机在抽屉布局下侧栏是 `position:fixed` 的 56px 轨道，不补这条 `margin-left:56px` 会直接盖住会话左侧（这是本次改动**引入**的回归点，必须同时修）。

### 4. `panelNav` 与其余 JS 消费点

`panelNav` 的渲染条件本身不用改（`:880` 仍是 `activePanelId !== null && !wideViewport`），它跟着 `wideViewport` 一起变；`viewportIsWide()`（`:374`）改用 `WIDE_LAYOUT_QUERY`，因此下面两处自动一致：

- 窄布局下点会话行后关闭抽屉（`closeDrawerAfterSessionAction`）；
- Android 返回键（`onNativeBack`）在横屏手机上先关抽屉、再退面板——与本次实验的设计前提（dsh-go 的横屏手机仍用抽屉、平板才常驻）一致；该前提来自任务描述，本仓库没有 dsh-go 源码可核对，属【推断】。

React 侧把 `viewportWidth` 单值状态换成 `{ width, height }`（`:691-702`），仍在 `resize` 的 rAF 里合并读取，旋转与窗口缩放都会重新判定。

### 5. 测试与浏览器检查

- `tests/mobile-layout.test.ts:602` 判定表：932×430 → narrow、909×1314 → wide、1363×860 → wide、899×1314 → narrow、900×599 → narrow、900×600 → wide、1920×1080 → wide。
- `tests/mobile-layout.test.ts:619` 新增：断言构建出的 CSS 宽带等于 `WIDE_LAYOUT_QUERY`、窄带是补集、`panelNav` 与 `matchMedia(WIDE_LAYOUT_QUERY)` 仍在源码里。
- 右侧面板判定表（`:684-712`）加高度列，并补 932×430（开抽屉时整幅浮层 932px；关抽屉时与 899px 窄带同规则 dock 419px）与 909×1314 / 1363×860。
- `scripts/smoke-mobile-layout-ownership.mjs`：`views` 增加 932×430、909×1314、1363×860（`:63-66`），断言分支改用 `docks(view)`（`:70`、`:139`、`:285`）——即真实 Chromium 里跑的就是新判定。

## 风险

1. **矮而宽的桌面窗口也会变窄布局。** 1400×500 的桌面窗口（或分屏）现在拿到抽屉布局。旧的 `min-width:900` 会把它当平板。这是有意的取舍：500px 高的持久侧栏本来就挤，但确实是一处用户可见的行为变化。若要收紧，可只对 `pointer: coarse` 应用短边地板，代价是桌面触屏与鼠标设备判定更复杂。
2. **软键盘可能压低视口高度。** 判定读 `window.innerHeight`，媒体查询读的是同一个布局视口，两者因此天然一致；但 Android Chrome 在键盘弹出时可能同时缩小布局视口高度——1363×860 平板横屏若被压到 <600 会在输入时翻成抽屉布局，键盘收起后翻回。本仓库没有 `interactive-widget`/`visualViewport` 相关处理，这一条未实测（无真机）。缓解方向：改用 `svh`/`screen` 短边，或加 `interactive-widget=resizes-content` 的显式声明。
3. **旋转时的重排。** 判定依赖 `resize` → rAF → state，旋转到横屏的瞬间会先按旧尺寸渲染一帧，然后切到抽屉布局；抽屉的 `data-open` 初值来自 `viewportIsWide()`（挂载时求值），旋转不会重置用户显式折叠过的侧栏——但横屏手机与平板之间来回旋转会保留上一形态的 `sidebarOpen` 状态。
4. **`src/mobile-sidebar-scroll.ts:41` 仍用 `(max-width:899px)`。** 横屏手机现在进抽屉布局，但侧栏滚动记忆适配器在该宽度下仍按「非专用视口」处理，即退回原生滚动行为。改前改后都不生效，不是回归，但两处窄带定义现在不一致。
5. **`scripts/smoke-dsh-composer.mjs:279,287` 仍用 `(min-width: 900px)`。** 它的 fixture 是 1000×812，新旧查询都为 true，因此检查结论不变；本次没有改它（该 smoke 需要 `@deepseek-ai/dsh` 宿主 bin，本机 worktree 里没有，跑不了就不改）。
